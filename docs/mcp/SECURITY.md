## 2. Ризики, які я вважаю реальними для цієї конфігурації

- **Prompt injection через дані.** У цій конфігурації жоден сервер не тягне контент ззовні (немає fetch, немає мережевих запитів). Однак `catalog.json` читається і filesystem-сервером, і catalog-сервером — якщо хтось модифікує JSON і вставить туди текст-інструкцію для агента (наприклад, `"name": "IGNORE ALL PREVIOUS INSTRUCTIONS..."`), агент може її виконати. Ризик низький, бо дані локальні й синтетичні, але в проді з user-generated content це був би реальний вектор.

- **Занадто широка область доступу.** Filesystem-сервер бачить увесь репозиторій, а не лише `app/data/`. Це означає, що агент може читати і змінювати будь-який файл проєкту — конфіги, документацію, `.mcp.json`. Для домашки це зручно (треба працювати з різними файлами), але scope ширший за мінімально необхідний. Окремо: filesystem-сервер має tools для запису (`write_file`, `edit_file`, `move_file`), які виходять за межі read-only принципу.

- **Витік секретів.** У цій конфігурації токенів немає — жоден сервер їх не потребує. `.env` у `.gitignore`. Проте `.mcp.json` містить абсолютні шляхи до домашнього каталогу (username у шляху), що закомічено в репо — це мінорний витік інформації про середовище.

- **Зміна поведінки сервера після встановлення.** Обидва публічні сервери запускаються з `@latest` (плаваючий тег). Якщо автор або supply chain атака змінить пакет — наступний `npx` завантажить нову версію автоматично. У навчальному репо це прийнятно, але в проді варто зафіксувати конкретну версію.

- **Дії з побічним ефектом.** Filesystem-сервер має tools для запису файлів — `write_file`, `edit_file`, `create_directory`, `move_file`. Агент може їх викликати (Claude Code запитує підтвердження, але це залежить від налаштувань хоста, а не від сервера). Memory-сервер теж пише на диск (`memory.json`). Власний catalog-server — суто read-only.

## 3. Що я зробив, щоб це зменшити

- Filesystem обмежено каталогом цього репозиторію, а не домашньою текою чи `/`. Сервер не бачить інші проєкти, SSH-ключі, `.env` файли поза репо.
- Власний catalog-server має виключно read-only tools — жодного tool для запису, видалення чи мережевих викликів.
- Секрети передаються через `${ENV_VAR}` у конфізі (зараз їх немає, але шаблон `.env.example` присутній). `.env` у `.gitignore`.
- `app/data/catalog.json` не редагується — це ground truth для Task D.
- Жоден сервер не має мережевого доступу (fetch не підключено).
- Хост (Claude Code) вимагає підтвердження перед викликом tools із побічними ефектами.

## 4. Що лишилось прийнятим ризиком

- **Версії серверів не зафіксовані** — використовується `@latest` для filesystem і memory. У навчальному репо це прийнятно (скорочує час налаштування), але в проді це supply chain ризик: пакет може змінитися між запусками.
- **Filesystem-сервер має scope ширший за мінімальний** — бачить увесь репо, а не лише `app/data/`. Вужчий scope ускладнив би виконання інших задач домашки (треба працювати з `docs/`, `mcp-server/` тощо).
- **Filesystem-сервер має write tools** — це не read-only сервер. Ризик пом'якшується тим, що хост вимагає підтвердження, але сервер сам по собі не обмежує запис.
- **Абсолютні шляхи в `.mcp.json`** містять username і закомічені в репо. У проді конфіг варто генерувати або використовувати відносні шляхи.
- **Memory-сервер пише `memory.json` на диск** — мінімальний ризик, файл локальний і не містить чутливих даних.
